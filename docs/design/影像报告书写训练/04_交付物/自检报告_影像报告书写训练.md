## 遗漏/问题清单

按法典 §6.4：**❌ = 硬阻塞**（必须修复后重跑自检）；**⚠️ = 软提醒**（不阻塞交付，但需说明原因）。

**本报告无 ❌ 项。**

### ⚠️ 1. 视觉规范：无 Step 0 JSON 预设，对齐对象改为两端各自 CSS 令牌

- **问题**：法典 §6.2「视觉规范」的通过标准写的是「符合步骤零确认的规范对象（JSON 预设）」，而本模块**未走 Step 0 的 JSON 预设流程**，改以两端各自的 `variables.css` 为对齐基准（学生侧 `apps/training/src/styles/variables.css`、承接侧 `apps/admin/src/styles/variables.css`）。
- **训练端实测偏差**（`css/tokens.css` 学生令牌段 36 项 vs `variables.css` 27 项）：
  | 令牌 | 原型 | 训练端 | 判定 |
  |---|---|---|---|
  | `--card-shadow` | `0 1px 3px rgba(0, 0, 0, 0.05), …` | `0 1px 3px rgba(0,0,0,0.05), …` | **实质等价**（仅空格排版差异） |
  | `--font-family` | 含 `'Segoe UI', 'Microsoft YaHei'` | 无这两族 | 原型外壳（中文回退）需要 |
  | `--sidebar-width` | `236px` | `200px` | 原型左栏多一个页面切换栏块，需更宽 |
- **训练端独有令牌 1 项**：`--tabbar-height`（移动端底部导航；本模块**不做移动端**，合理不采用）
- **管理端令牌（第五轮新增）**：`css/tokens.css` 追加 `--adm-*` 令牌块 **10 项**（`--adm-primary #1890FF` / `--adm-primary-dark #096DD9` / `--adm-primary-light #E6F7FF` / `--adm-header-bg #1A5F9E` / `--adm-sidebar-bg #2B3A4A` / `--adm-sidebar-text` / `--adm-border #E8E8E8` / `--adm-bg #F0F2F5` / `--adm-card-radius 12px` / `--adm-content-max-width 1400px`），色值与 `apps/admin/src/styles/variables.css` 的核心外壳项**逐条一致**。
- **管理端已知偏差**：`apps/admin/src/styles/variables.css` 共 **60** 个令牌，原型只提了 **10 个外壳级** `--adm-*`；管理端组件级语义色（success / warning / error / purple 系）在 `css/admin.css` 中**直接写色值**（32 个不同 hex、16 处 `var(--adm-*)` 引用），未逐条令牌化。判定为**演示层自限**——管理端页在本模块定位是契约承载（题库/组卷/成绩的字段与门禁行为），不是 `apps/admin` 的视觉复刻；未接入其完整令牌体系属已知取舍。
- **原型独有令牌 10 项**：`--error-border` `--error-light` `--font-mono` `--reqpanel-width` `--shell-min-width` `--success-border` `--success-light` `--text-inverse` `--warning-border` `--warning-light`
- **修复方案**：不修。理由——上述差异**全部来自原型外壳**（侧栏、需求面板、串讲编辑）与**管理端演示层**，产品界面的颜色/字号/圆角/间距令牌与两端 `variables.css` 逐条一致；把外壳令牌强行并入产品变量表反而会污染产品视觉基线。已在 `blueprint.md` 第九节与本节显式登记。

### ⚠️ 3. `data-act="noop"` 为刻意占位，非幽灵绑定

- **问题**：法典 §6.2「交互完整性」要求「所有绑定的函数均有实际逻辑（非空、非纯 alert、非 TODO）」。原型中存在 `data-act="noop"`。
- **核查结论**：`noop` 共 **49 处**（学生侧 P1–P8 **17 处** + 承接侧 P9–P13 **32 处**；第四轮报告记为"8 处"，系**漏计**，本轮按文件重新清点校准），**不是**无处理器的幽灵绑定——`js/app.js:139` 有明确分支：按钮类元素与 banner 关闭按钮点击时弹 `原型演示：此处仅为状态呈现，不触发真实业务`。这是**有意设计**：让"不该有真实行为"的控件（如纯展示型按钮）给出明确反馈，而不是静默无响应。
- **修复方案**：不修。判 ⚠️ 而非 ❌，理由是该动作**有实际逻辑**（用户可感知的反馈），只是逻辑为"说明性"的。

### ⚠️ 5b. 验证手段本身的缺口（本轮最值得记的一条）

**问题**：Step 5 与第五轮对原型的验证用的是**关键词断言**——断言某串文字在不在 DOM 里。这对 F3 这一类缺陷**完全不敏感**：被转义的标签**仍然是那串文字**（`&lt;b&gt;` 里就含 `b`），`grep` 照样命中，于是断言全绿，页面却在裸奔。

2. **静态检测脚本**：扫 `H.rich(` / `H.ed(` 实参里的字符串字面量是否含 `<tag>`。**比渲染扫描更可靠**——条件分支（P4 未提交态、P7 未触发门禁态）**不渲染时也能查到**。**结果：0 命中**。

**为何判 ⚠️ 而非 ❌**：三项缺陷**均已修复并验证**，不构成交付阻塞；登记在此是为了说明「验证覆盖到了什么程度」，以及**关键词断言不等于视觉正确**这条方法论。

- **给下一个模块的建议**：原型类交付物的验收应至少叠一层渲染后扫描（查字面转义标签、查 `undefined` / `NaN` / `[object Object]` 漏出），不要只用关键词断言。
